Layout Skill Bench — three skills, one brief

One local model — Qwen3.8 Flash Next (MLX) — built the same deliverable three times: five landing-page iterations for a note-taking “second brain” app, with an easy switcher between them. Every run received the same byte-identical verbatim brief and ran on the same model in the same harness (opencode). The one thing that changed between runs was the design skill loaded. Every figure on this page comes from bench/layout-skill-bench/results/arms.json, the single source; a value that was not collected would render as a gap (—), never zero. This is a controlled comparison of three different skills, not one skill against a baseline and not one configuration run twice.

“I want you to design the landing page for a note-taking application as essentially a second brain. You should design five iterations and each of them should be accessible within the slash one, slash two, slash three like pages directory. And then you should add a little button that lets me switch between them easily.” The verbatim brief — SHA eaebe847…, 318 characters, byte-identical across all three runs (confirmed against the opencode session database).

What the comparison holds and what it varies read this before the grid

Held identical across all three runs

  • The brief — the exact 318-character text above, SHA eaebe847…, byte-identical in every run.
  • The model — Qwen3.8 Flash Next, MLX, on the local rig, at zero API cost.
  • The harness — opencode, one session per run.
  • The task — five landing-page iterations plus a switcher; every run shipped exactly 5 pages.

Varied — one design skill per run

    Why this is three skills, not two — and not one skill vs. a no-skill baseline

    taste-skill and taste2 ship a byte-identical skills-lock.json (both pin brandkit, design-taste-frontend and high-end-visual-design from Leonxlnx/taste-skill). A lock file records which skills were available, not which one fired. Reading each session's actual transcript shows different skills ran: taste-skill invoked design-taste-frontend (an 87,308-character skill message) and taste2 invoked high-end-visual-design (a 10,476-character one). brandkit appears in neither session. So the two arms are not a repeat run of one configuration.

    design-skill has no lock file at all — it is not part of the Leonxlnx/taste-skill package. Its transcript shows it loaded frontend-design from the user's global skill directory, so it is not a no-skill baseline either. Each of the three ran a real, different design skill.

    Limits, stated plainly

    • Wall time and token cost are not proxies for design quality. They reflect how much the loaded skill asked the model to do (taste-skill’s ~87KB skill document versus taste2’s ~10KB one, versus design-skill’s skill and brief combined into a single message) more than any inherent difference between the three skills’ output.
    • Only design-skill combined the skill and the brief into one message; the other two received them as two separate user turns. That is a difference in session setup, not in the words of the brief.
    • taste2 is the only run with a mid-run auto-compaction event and an extra “continue” nudge — its messages count (19) includes both, alongside the two substantive turns the other two runs also have.
    • All three ran on the same local model at zero API cost. This bench does not compare cost or hosted-model behavior at all — only skill choice under identical local conditions.
    • The three runs shipped different forms (static HTML directories, a Vite + React app, static pages behind a small Node server), so the grid links below take three different shapes; a later publish step rewrites two of them to serve under the site.
