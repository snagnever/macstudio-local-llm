Benchmark · Apple M4 Max 128 GB · October 2026

The best way to run Qwen3.8-Flash-Next on an M4 Max 128 GB

Five local inference servers, the same model and its Swift 1.5 fine-tune, contexts from 8K to 1M tokens. I measured what you wait for in a real agent session, not only tokens per second.

Chip Apple M4 MaxGPU 40 cores · Metal 4Unified memory 128 GBmacOS 26.6.2Measured 2026-10-07 to 2026-10-25

Result: Splash 1.4.0 with the unsloth UD-IQ4_XS GGUF has the shortest agent turn at every context size: 6.8 s at 128K, 7.3 s at 512K, 10.5 s at 1M. It is the only server that reached 1M. Its cost: a change halfway in the history prefills the whole prompt again. If your agent edits, compacts or forks the history often, use mlx-serve 26.10.3 with the ddalcu iQ-MLX 4.7 bpw quant (8.9 s at 128K, 14.5 s at 512K). Conclusion · commands.

Goal

Find the best stack to run Qwen3.8-Flash-Next as a daily driver on one Mac Studio (M4 Max, 128 GB). The model is a 125B mixture-of-experts with 6B active parameters and a native context of 262K tokens, so it fits in 128 GB at 4 to 6 bits per weight and decodes fast.

Weights

The four servers of the October round each run the pack the runtime's author publishes for it, in the runtime's own format: the current ddalcu pack for mlx-serve, the only oMLX pack for Flash-Next, the pack MTPLX recommends for 128 GB Macs, and the larger of the two ds4 GGUFs, chosen for quality parity. The files are as close to each other as the formats allow (4.7 to 5.97 bits per weight), but they are not identical. The quality check in section 12 shows the three servers I checked within a few cases of each other; ds4 and Splash with the base model were not checked. Splash loads Flash-Next from a GGUF only: it runs the base model as the unsloth UD-IQ4_XS GGUF. The two Swift 1.5 stacks run a community fine-tune: in MLX on mlx-serve, and as a GGUF on Splash.

Precision

A personal test for my own daily use and curiosity, not a lab benchmark. I aimed for accurate numbers without letting the runs take days: one machine, one test prompt, 1 to 3 runs per point. Small differences can be run-to-run variation.

    2 · At a glance: Splash is the fastest, with the base model and with Swift 1.5

    Five speed metrics and the largest context, one panel each. Pick a context size. Among the five servers that run the base model, Splash has the shortest agent turn, the fastest next-turn TTFT and the fastest decode at every size I tested, and it is the only one that reached 1M. mlx-serve has the fastest cold prompt, by up to 7%, and it leads the three MLX servers in every panel. With Swift 1.5, Splash is faster again.

    Context size

    The trade-off is memory: mlx-serve locks 106 GB at 128K and Splash 113–115 GB, against 90–110 GB for oMLX, MTPLX and ds4 (memory chart). No server used swap.

    3 · Agent turn time: Splash is the fastest at every context size, mlx-serve among the MLX servers

    Agent turn time = the wait from sending a tool result to the end of a 512-token reply: TTFT (time to first token) + 512 ÷ decode speed. A coding agent pays this at every step. Lower is better.

    • Splash with the base model is almost flat: 7.2 s at 8K, 6.8 s at 128K, 7.3 s at 512K and 10.5 s at 1M.
    • mlx-serve is the fastest MLX server: 7.9 s at 8K, 8.9 s at 128K, 14.5 s at 512K.
    • oMLX is second at 128K and 256K (12.1 and 14.5 s). MTPLX is close at 32K (8.8 s), but needs a flag to reach 128K and refuses 256K.
    • ds4 serves every size up to 512K, but its turn grows from 12.6 s at 32K to 61.9 s at 512K.
    • Swift 1.5 on Splash takes 6.2 s at 8K, 6.3 s at 128K, 6.7 s at 512K and 9.3 s at 1M. The same fine-tune on mlx-serve 26.10.3 takes 8.9 s at 128K and 12.7 s at 512K (section 9).

    4 · The first message is slow on every server. The next one is what you feel.

    In an agent session, every step sends the whole conversation again: system prompt, files, earlier replies and tool results, plus a small new part at the end. A server with a prefix cache keeps the already processed part and prefills only the new tokens. Without a cache hit, the step prefills the whole prompt again.

    mlx-serve at 512K. The bar lengths are schematic; the times are measured.

    13 min → 4.1 s At 512K, mlx-serve needs 13 minutes to prefill the full prompt the first time. With a cache hit, the next reply starts after 4.1 s, about 190× faster. No server prefilled faster than 832 tokens/s on this machine, so the first message is slow everywhere. The cache makes the difference.

    The wait is the tokens that miss the cache, divided by the prefill speed. The scenario only decides how many tokens miss. On this machine at 512K: 1K ≈ 1.5 s · 10K ≈ 15 s · 100K ≈ 2.5 min · 300K ≈ 7.5 min · 512K ≈ 13 min.

    5 · At long context, a 95% cache hit is not enough

    All seven stacks have a high cache hit rate on the next turn. At 512K the part that misses can still be a lot of tokens. ds4 hits 94.5% and prefills about 29K tokens again, so its next reply starts after 50 s. mlx-serve hits 99.8%, prefills about 1K tokens and starts after 4.1 s.

    8 · What each server can serve on 128 GB

    The model's native context is 262,144 tokens. 512K uses YaRN 2.0, a context extension that oMLX does not support. 1M ran only on Splash, which turns YaRN on by itself above 262K and keeps the KV cache past about 860K tokens on its SSD cache.       Splash is Inco AI's inference engine on native Metal. It loads Flash-Next from a GGUF only, so I ran it with two GGUFs: the base model as the unsloth UD-IQ4_XS, and the Swift 1.5 fine-tune as the ukisai IQ4_XS. The two stacks differ in runtime and in weight format, so the gap belongs to the stack, not to the server alone.

      • The base model on Splash. 7.0 s per agent turn at 256K, 7.3 s at 512K and 10.5 s at 1M, against 11.9 and 14.5 s for the iQ pack on mlx-serve. Swift 1.5 on Splash is faster again, by 0.4 to 1.2 s per turn. At 512K, 5 of 13 replies of the base model reached the 4,096-token limit while it was still reasoning.
      • The gain comes from decode. Splash writes 106 tokens/s at 256K against 74 on mlx-serve, and 107 against 57 at 512K. The first message costs the same: the cold prefill runs at 731 and 732 tokens/s at 256K.
      • 1M. Above 262K Splash turns YaRN on by itself. With the 8-bit KV cache, about 860K tokens stay in memory and the rest goes to its SSD cache: 9.3 s per agent turn, 2.6 s to start the next reply, 77 tokens/s, 110 GB of peak memory.
      • A change halfway costs the whole prompt. Flash-Next is a hybrid model: some layers carry a recurrent state that cannot be rolled back, and Splash saves that state only where a request ends. An edit of an earlier message, a compaction, a retried turn or a fork before that point reuses none of the prompt, against 44% on mlx-serve at 512K: 12 min at 512K and 25.5 min at 1M (splash #387, #361).
      • mlx-serve at 1M. With YaRN 3.815 and the 4-bit KV cache, mlx-serve 26.10.3 starts at 1M and serves the first message (28.6 min), but the next requests fail with PrefillDoesNotFit: they need about 18 GB for the prefill, and 7 to 9 GB are free. 2 of 5 requests failed with Swift 1.5 and 3 of 5 with the iQ pack, so the page has no 1M turn time for mlx-serve.
      • YaRN changes short answers too. Above 262K the context extension is static, so it applies to every prompt. Use the 512K or 1M setting only when the context needs it.

      Conclusion

      Use Splash 1.4.0 with the unsloth UD-IQ4_XS GGUF for the shortest agent turn. Use mlx-serve 26.10.3 with the ddalcu iQ-MLX 4.7 bpw quant when the history changes often.

      Among the five servers that run the base model, Splash had the shortest agent turn at every context size, from 8K to 1M, and it is the only one that served 1M. The cost is the cache: a change halfway in the history (an edit of an earlier message, a compaction, a fork) prefills the whole prompt again, 13 min at 512K against 8 min on mlx-serve. I did not check the quality of the base model on Splash. mlx-serve leads the MLX servers, and the runner-up among them is oMLX 0.7.0 (12.1 s at 128K), but it stops at 256K. Commands below. With Swift 1.5, Splash is faster again (6.7 s at 512K, 9.3 s at 1M, section 9). On mlx-serve 26.10.3 the iQ pack is slower past 128K, and Swift 1.5 is the faster quant there (same-build table).

      • The prefix cache flags matter. In my September test (mlx-serve 26.9.1), the default 2 GB cache could not hold a 128K session, and every turn read the whole prompt again.
      • For 512K, use the 4-bit KV cache. With 8-bit, some long prompts were refused because they did not fit in memory.

      11 · Tips for daily use

      • Keep the start of the prompt stable. System prompt, tool list and project rules come first. A change there invalidates the cache for everything after it.
      • Add to the end; avoid changes earlier in the history. At 512K, a change halfway (a fork, a compaction, an edit of an earlier message) costs 8 min on mlx-serve, because ~293K tokens are prefilled again, and 13 min on Splash, which prefills the whole prompt. A new message at the end costs seconds.
      • The first load is paid in parts. Prefilling a cold 128K prompt takes about 3 min, 512K about 13 min, but only a session that starts that large pays it at once. In daily use the context grows step by step and each step prefills only the new part. Keep working in the same session.
      • Leave memory headroom. mlx-serve locks 100–114 GB from 32K to 512K.
      • Use the context you need. The turn grows from 8.9 s at 128K to 14.5 s at 512K, and 512K needs the 4-bit KV cache.

      13 · Bonus: Swift 1.5, a fine-tune on the same stack

      Swift 1.5 is a community fine-tune of Qwen3.8-Flash-Next that thinks less before it answers. I ran it on the same mlx-serve setup. It scored the same as the base quant within the noise of these samples, and it reached the final answer 2.9× faster on GPQA and 2.0× faster on LiveCodeBench. Its agent turn time is the same, because prefill and the cache do not change. I now use it every day.

      14 · How I measured

      Test prompt
      A long audit document filled to the target size, with three facts hidden at 10%, 50% and 90% of the text. A reply is correct when it finds all three.
      Scenarios
      First message: the full prompt, no cache (cold prefill). Next turn: the same prompt plus a tool result at the end. User adds a message: the same prompt plus a new user message. History changes halfway: the prompt changes at its midpoint, so only the first half can be a cache hit. This is what a fork, a compaction or an edit of an earlier message does to the cache.
      Agent turn time
      TTFT on the next turn + 512 ÷ median decode speed. It is the wait for one agent step with a 512-token reply.
      Runs
      One to three runs per point; the "Runs" column of the last table gives the number. A point with three runs shows the median.
      Speculative decoding (MTP)
      The model has a small extra head that drafts the next tokens; the server checks them in one pass. Output stays the same, decode gets faster.
      YaRN
      A method that stretches the model's position encoding beyond its native 262K tokens.
      Harness
      A script sends each scenario to the server's HTTP API and reads the timings from the stream. No coding agent sits in the loop.
      Data and scripts
      The raw results, the prompt generator and this page's script are in the repository (bench/engine-updates-2026-10, bench/swift15-flashnext-2026-10, bench/stack-updates-2026-10 and bench/splash-longctx-2026-10).

      What this page does not measure

      • Agent reliability over many turns. Speed, cache and memory only. Test your own agent workload before you choose.
      • Other chips. Numbers from an M5 Max or an M3 Ultra do not transfer to this M4 Max, and the reverse is also true.
      • Power draw and fan noise.
      • Several requests at once. Every run sent one request at a time.
      • The quality of ds4. Only the three MLX servers of the October round (section 12) and Swift 1.5 on Splash and mlx-serve 26.10.3 (section 9) went through a quality check.

      Setup notes

      • MTPLX. The default config plans only a 65,536-token window on this machine and refuses 128K; 128K needs --memory-limit max. Short requests without history skip its session cache, so the test sends a 64-token warm-up first.
      • Splash. It refuses Flash-Next in MLX format, so it cannot run the same file as mlx-serve. Clients must send frequency_penalty 0, as with mlx-serve 26.10.3: with 1, the tool-call test failed on both servers.
