How many agent sessions fit on one local Flash-Next server?

We ran several agent sessions at once against one local server: the Dankpaws Swift 1.5 Qwen3.8 Flash-Next MLX 4.7 bpw model on mlx-serve 26.10.1, on the test machine (Mac Studio M4 Max 128 GB), on 2026-10-17 and 2026-10-18. Two sessions work and stay within the pass rule, but each turn takes about twice as long, so two tasks run together finish no sooner than the same tasks one after the other. Update: the same tests on Splash 1.5.0 (partial results).

Maximum that passes

2 sessions

Two sessions pass the rule with a warning: worst slowdown 1.76× at 32K and 1.94× at 128K. Three and four sessions fail.

~2× slower

How the test works

Each session replays a coding agent’s conversation at a fixed context size. It starts cold: the server reads the whole prompt once (prefill, reading the prompt before the first token). Then come warm turns that add a tool result to a prompt the server already holds in its prompt cache and ask for a 512-token reply (decode, generating the reply token by token).

The turn time is the time from sending a tool result to receiving the full reply. The slowdown is a session’s turn time divided by the same session alone: 7.9 s at 32K, 8.6 s at 128K and 11.1 s at 256K.

A test configuration is a number of sessions × a context size × with or without short side requests: one-second permission checks, like an agent asking “may I run this?”, sent while the sessions work. Each configuration ran 3 times unless noted.

Pass rule: worst slowdown ≤ 1.5× passes; 1.5–2.0× passes with a warning; above 2.0× fails. The slowest session decides. A configuration also fails if the server refuses a request or a session misses more recall checks (a fact planted in the prompt that the reply must find) than its rule allows: at least 11 of every 13 answered checks (85%) per session at 256K; none missed at 32K and 128K (a reply cut off at its length limit does not count); none missed with the 8-bit KV cache. Recall counts only answered requests.

Why two sessions do not add up

The server already batches the sessions’ generation: it writes one token for each session in the same step. On this model that step gets slower as sessions are added, so the total grows little. Going from 1 to 4 sessions, the best total grows at most 1.44× the speed of one session alone at 32K and 1.26× at 128K, while each session slows down by more.

Short side requests wait for long prompts

A side request takes about a second when the server is free. When it arrives while another session is reading a long prompt, it waits for that read to finish: a cold 128K prompt takes about 166 s to read and a 256K one about 351 s (one session alone, median). At 32K the slowest side requests (95th percentile) took 22.0 s–41.1 s; at 128K and 256K, 168.1 s–358.6 s.

Does --max-concurrent matter?

--max-concurrent sets how many requests the server runs at once. On mlx-serve 26.10.1 the default is 1, yet the boot log already says Concurrency: --max-concurrent=1, batched decode on: two sessions share generation either way. The flag is not a queue, and setting it to 2 changes nothing measurable. At 128K the side-request p95 is higher with the flag at 2 because of a single very slow request; the count of side requests over 60 s is close in both runs.

256K: two long sessions

Two 256K sessions fit only when the prompt cache kept in RAM is cut from 16 GB to 4 GB. That configuration passes with a warning: worst slowdown 1.68× against the 11.1 s reference, or 1.81× against the 10.3 s we measured for one 256K session alone over 3 runs. With the 4 GB cache, warm turns lose about a second restoring the cache from the SSD.

Two real Claude Code sessions

Two real Claude Code 2.1.292 sessions (claude -p) shared the everyday server setup (128K context, default --max-concurrent 1), each on a fixed coding task with the same model as both main and fast model. Every task was done, with no errors and no refusals. Each session took 1.84×–2.36× its time alone, above the 1.5× rule.

--prefill-decode-share 0.3 and 0.5

--prefill-decode-share makes generation keep a share of the time while another request reads its prompt. We tried it at 128K to clear the side-request wait. It did not: as many side requests waited over 60 s as without it, and the cold first token took about twice as long. Not adopted.

What we learned

  1. mlx-serve 26.10.1 already batches generation for this model at the default --max-concurrent 1; the flag is not a queue.
  2. Two sessions is the most that passes: 1.76× at 32K and 1.94× at 128K. Three fail (2.37× / 2.36×), four fail (3.37× / 3.85× with side requests, 2.84× / 3.66× without).
  3. Total generation speed grows little with more sessions, so two sessions together are not faster: two real Claude Code tasks took 147.6 s together against 137.6 s one after the other.
  4. A short request that arrives while another session reads a long prompt waits for it (p95 168.1 s–358.6 s at 128K and 256K); neither --max-concurrent nor --prefill-decode-share removes the wait.
  5. Two 256K sessions fit only with a 4 GB prompt cache in RAM; with 16 GB or an 8-bit KV cache the server refused requests or the model missed a recall check.
  6. The everyday server setup stays as it was. The launcher gained a 256k profile for two long sessions.

Admission refusals

Some requests were refused before the server started reading them: 4 sessions + side requests, 128K; 256K + 32K sessions, 16 GB prompt cache; 2 × 256K, 8-bit KV cache. One of the server’s messages, verbatim:

prompt 125549 tokens needs ~6266MB at prefill chunk 512 (the narrowest width tried), ~5968MB available + ~13863MB the hot cache can give back (~17420MB resident, ~3556MB of it pinned by this request's own prefix) — refused before prefill

Read literally, the message lists more memory available plus memory the prompt cache can give back than the request needs, even after leaving out the part pinned by the request’s own prefix. It looks like an admission accounting problem in this server version, similar to issue #528, whose fix is already in this version. Cause not confirmed.

Not measured

  • The iQ-MLX 4.7 bpw build of the same model with two sessions.
  • 512K with two sessions (the 512K launcher profile forces one request at a time).
  • mlx-serve 26.10.2, which changes batching at long context and the SSD cache, and PR #884 in a future release.
  • More than four sessions. Three sessions ran only with side requests.
  • A real queue in the client (a lock that sends one request at a time) on mlx-serve: this server version has no switch to turn batching off. The Splash update above measures it on Splash.
  • An interactive Claude Code pair with real permission prompts and titles.
