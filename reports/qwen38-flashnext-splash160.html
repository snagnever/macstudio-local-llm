Splash 1.6.0 vs 1.5.0

Stay on Splash 1.5.0 if you run two long sessions. Two 256K sessions are up to 65% slower on 1.6.0, because requests wait for memory (claim_wait up to 30.1 s). A single stream runs at the same speed. Under a memory limit, 1.6.0 is clearly better. The #644 decode drop did not appear on either release.

Update, 2026-11-12: Splash 1.6.1 removes this slowdown. Two 256K sessions run 3.5% slower than on 1.5.0, with no memory wait, and my launcher now runs 1.6.1 (Splash 1.6.1 page).

Task 4. Does the new scheduler change the cost of a second session?

fail

Yes, for two 256K sessions. On 1.6.0 the worst stream is 65% slower than on 1.5.0 the same day. The likely cause is the new memory governor: a request waits for memory (claim_wait) for up to 30.1 s. The wait appears only with two sessions of 128K or more, and the maximum of about 30 s in both arms suggests a fixed timeout. The summed decode is the same on both releases that day, so the loss is in time to first token. Sessions at 32K and 128K and one session do not get worse. 1.5.0 numbers marked 2026-10-29 come from another day; the 256K pair has a same-day 1.5.0 control with 1 rep.

API contract notes

  • The API key no longer goes to the proxy. With http_proxy set, the 1.5.0 launcher sent 1 request with the key through the proxy (GET /v1/models) and then did not find the server. 1.6.0 sent none and gives the agent NO_PROXY=127.0.0.1,localhost,::1. The rig had no http_proxy in its SSH session, so no key leaked during the campaign. No key value is stored in the results.
  • The engine restarts in seconds, with documented 503s. After a SIGKILL of serve-native during a stream, the stream ends with a runtime_unavailable error event and [DONE]. Retries get 503 with Retry-After (engine_recovering ×23, runtime_unavailable ×1), the codes that api.md documents. The first 200 comes at 24.3 s, within 2 × the 30 s boot, and the context stays 32768.
  • KV reuse past a thinking cut, announced for 1.6.0, was not observed on either release. With thinking_token_budget 1024 and a tool, the second turn cached 320 tokens on both releases: the 332-token first prompt rounded to the 32-token block, and none of the reply. 1.6.0 cut the thinking in all 3 valid reps (1313, 1213, 1129 output tokens); 1.5.0 hit max_tokens 4096 in 1 of 2. This is not a regression.
  • Two request shapes now fail on 1.6.0. stop_sequences as a string and a stop string of 16385 characters get 400. Clients that send either need a change. /status moves to schema 8.

Method and limits

  • One rig (Mac Studio M4 Max 128 GB), one model at a time, the same weights on both releases: ukisai Swift 1.5 Qwen3.8 Flash-Next GGUF IQ4_XS (revision 0142554). Base flags --verify-rows auto --idle-release off --language-only --no-webui --offline.
  • Sampling: temperature 1.0, top_p 0.95, top_k 20, reasoning effort xhigh. Claude Code 2.1.292, the version of the earlier baselines.
  • Single-stream turns: 3 boots per release and band in ABBA order, an idle gate between bands and 120 s between arms. Speed gates: no HTTP errors, correct needles, cache hit ≥ 0.90, swap growth ≤ 0.5 GB.
  • Decode drop: a 64-token probe after the load ÷ the same probe before it. ≥ 0.85 is stable, 0.50 to 0.85 degraded, below 0.50 a drop. The probe varies about ±8% between single reps, so it runs 3 reps.
  • Stall gate: largest gap between chunks ≤ 10 s and p99 ≤ 5 s, with every request answered.
  • Controls with 1 rep: the 1.5.0 pair of 256K sessions and the 1.5.0 1M run. The Claude Code minimum tok/s comes from a single request per profile.
  • Task 7 runs once per release, in sequence. Its per-hour table places each pair by the summed wall time of the earlier pairs and probes; the stage report used file times, and both give the same pairs per hour.
  • Warm TTFT of Claude Code sessions uses the warm definition of claude_requests.py (cached prompt and at most 2000 new tokens) in Task 4 and Task 7 alike.
  • Every number on this page is computed from the committed results by bench/splash16-2026-11/scripts/render_page.py, except the API check table, which restates the Task 1 stage report.
