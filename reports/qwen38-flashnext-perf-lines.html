Qwen3.8-Flash-Next: four runtimes from 8K to 512K

The same model on four runtimes, with the same fixture and the vendor sampling: mlx-serve 26.10.1, oMLX 0.7.0, MTPLX 2.12.2 and ds4. The September daily driver (c1) is the reference line. Each panel is one metric; each line is one runtime. Hover over a chart to read the values by context.

Apple M4 Max · 128 GB · measured 2026-10-07 to 2026-10-09. mlx-serve 26.10.1 · oMLX 0.7.0 · MTPLX 2.12.2 · ds4 upstream 0aaea5a. c1 = September reference (mlx-serve 26.9.2).

  • Speed, cache and memory only. This page does not measure agent reliability. A community test on an M4 Max 128 GB found differences between these runtimes in multi-turn agent tasks (zenn.dev). Test your own agent workload before you choose.
  • The chip changes the result. Public numbers from an M5 Max or an M3 Ultra do not transfer to this M4 Max. The prefill ratio between oMLX and mlx-serve changes with the chip (mlx-serve issue #658).
  • MTPLX needs a 64-token prime. MTPLX runs a request with max_tokens ≤ 48 and no history as a background task, without a session, so it does not keep the prefix. The probe primes MTPLX with a 64-token prime. MTPLX runs from the 1-token prime are left out of this page.

Rig

Setup by candidate

What changes between runtimes: runtime, quant, prefix cache mechanism and speculation. Sampling is the same for all of them (vendor): temperature 1.0, top_p 0.95, top_k 20, reasoning xhigh, max_tokens 4096. Fixture audit_retrieval with needles at 10/50/90%. Native context: 262,144 tokens; 512K uses YaRN 2.0.

Runtimes compared

All four runtimes do speculative decoding with MTP and prefix caching on Apple Silicon. They differ in where the KV cache lives (RAM, disk or paged SSD) and in how they handle the memory limit: mlx-serve pins it as wired memory, oMLX spills over to SSD, MTPLX refuses the prompt and ds4 keeps the prefix cache on disk.
