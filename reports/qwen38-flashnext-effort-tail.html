Where the thinking-effort line goes decides what the prefix cache can reuse

The same effort line, first or last in the prompt, on two 4.7-bit MLX packs (Swift 1.5 and iQ-MLX): effort switches at 128K, short tool-calling prompts, obedience to the level, and time, tokens and accuracy at xhigh, medium and low.

Qwen3.8-Flash-Next takes its thinking effort from one line of the prompt. Put that line first (the official template) and changing the effort in a 128K session costs 167 s, because the whole prefix cache is lost. Put it last and the switch costs 0.8–5.8 s, the model still obeys it, and accuracy holds. But the same move breaks prefix reuse on short prompts: every tool-calling turn starts cold, +0.9 to +1.4 s. On a hybrid attention/SSM model, where a variable line sits decides where the server can save its state.

What we learned

  • Where the effort line sits is a cache decision, not a prompt-engineering one. The model obeys it in either position. The server's prefix cache does not: with a hybrid GDN/SSM model, mlx-serve can only resume at a saved state checkpoint, and the checkpoint goes at the start of the last message.
  • Tail template: good for long sessions, bad for short ones. Effort switch at 128K: 167 s → 0.8–5.8 s. Same-effort control turn at 128K: 1.3 s → 3.0 s. Short tool-calling turn: +0.9 to +1.4 s, prefix reuse 53/55 → 0/55.
  • Both packs behave the same way. Swift 1.5 and iQ-MLX give the same cache hits at every step of the probe (0.97–1.00 on switch, 0.98 on control) and pass the same accuracy rules.
  • iQ-MLX cuts more thinking per level than Swift 1.5. At low, iQ-MLX thinks ×0.26 of its xhigh; Swift 1.5 ×0.45. Swift 1.5 thinks less to begin with (GPQA median 1.7K vs 5.1K tokens at xhigh on the earlier page).
  • At xhigh, the tail template hits the token limit a little more often (Swift 4 → 7 in 2 rounds, iQ 7 → 9 in 1), and its thinking ratio leans to ×1.04–×1.05. The intervals include 1.0, so this is not confirmed.
  • Decision: the official template stays the default; the harness fixes the effort per session (xhigh for code and long sessions, medium for chat and short tool calling). The tail template is kept as an optional profile for long sessions that need to change effort mid-way. Five untested ways to keep both the cheap switch and the short-prompt cache are listed below.

The two templates

Qwen3.8-Flash-Next reads its thinking effort (reasoning_effort: low, medium or xhigh) from one line in the prompt. The official chat template writes that line first. The effort-tail template moves it to a short system block after the last message. Nothing else changes: at medium the two templates render the same prompt.

Switching the effort in a long session

Probe 3e: a 128K-token conversation at xhigh, then one turn at medium or low, then back to xhigh. With the official template the effort line is the first token of the prompt, so changing it invalidates the whole prefix cache and the server re-reads 126K tokens: 167 s before the first token. With the effort line at the tail, the history stays cached and the switch costs 0.8–5.8 s. Median of 2 rounds per switch; the iQ-MLX official template was not re-run here, since its prompt is identical to the Swift one.

Short prompts lose the prefix cache

Probe 3f, Swift 1.5: 55 tool-calling cases that share the system prompt and the tool list (600–1,200 tokens each). With the official template the server reused the shared prefix in 53 of 55 requests. With the effort line at the tail it reused it in 0 of 55: every request paid the full prefill, +0.9 to +1.4 s on the first turn. Accuracy did not change (36→37 of 40, 10→10 of 12). This regression is why the tail template did not become the default.

officialeffort tail correct wrong× hit the max_tokens limit median

Why. Qwen3.8-Flash-Next is a hybrid model: its attention layers keep one entry per token, but its Gated DeltaNet (SSM) layers keep one state that summarizes everything read so far. To resume from a cached prefix the server needs a saved copy of that state, a checkpoint, inside the part of the prompt that stayed equal. The logs show one checkpoint at the start of the last message. With the official template that message is the user question, right after the shared prefix, so the checkpoint is inside it. With the tail template the last message is the effort block, after the question, so when the question changes no checkpoint falls inside the equal part and the server starts cold (hybrid miss (no checkpoint ≤ 555 of 618); cold prefill). At 128K the periodic checkpoints (--ssm-checkpoint-stride) fall inside the history, so long sessions do not have this problem.

The model still obeys the effort line at the tail

Paired test on the same 100 questions (GPQA-Diamond 50 + LiveCodeBench 50): thinking tokens per question, geometric mean of the ratio, 90% bootstrap interval. Swift 1.5 has 2 rounds per arm; iQ-MLX has 1. The medium prompt is identical in both templates, so its ratio is an A/A test that shows the noise floor.

Ways to keep both: a cheap switch and the short-prompt cache

Five options, none tested yet, written down on 2026-10-17. They all rest on the checkpoint rule inferred from the logs (one checkpoint at the start of the last message); confirming that rule in the mlx-serve source comes before options 4 and 5. Dashed blocks are the part that stays equal between the two requests of each diagram.

1. Effort block before the last user message (template)

The last message is the user question again, so the checkpoint returns to the end of the shared prefix. Short prompts reuse the system prompt as with the official template; an effort switch at 128K keeps the history and re-reads only the effort block and the last question.

Cost: in a long session every new question moves the effort block, so the server re-reads the whole previous turn (its question, tool results and answer). The cost is bounded by one turn, not by the session. Test: probes 3e and 3f and the obedience battery of Task 11, plus a short 3c to measure the control turn.

2. Smaller --ssm-checkpoint-stride

Keep the tail template and let the server write periodic checkpoints inside short prompts. With a stride of 512 tokens, a 600–1,200-token prompt gets one or two checkpoints inside the shared prefix.

stride todaysystemtoolsuser: questioneffortassistant
stride 512systemtoolsuser: questioneffortassistant

Cost: the server help says each checkpoint forces a chunk boundary and re-reads the expert weights during prefill, and each one stores a copy of the GDN state. Reuse is partial: it stops at the last checkpoint before the end of the shared prefix. Test: prefill time and memory at 32K, 128K and 256K, then probe 3f.

3. Hybrid template by conversation length

The Jinja template can count messages and characters. With few messages the effort line goes first (short-prompt cache intact); past a threshold it goes last (cheap switch). A session pays one full prefill when it crosses the threshold.

few messageseffortsystemtoolsuser: questionassistant
many messagessystemlong historyuser Neffortassistant

Cost: the threshold is fixed in the template and invisible to the client. No server change. A fallback if option 1 regresses on long sessions.

4. A checkpoint at every message boundary (mlx-serve)

If the server saved the SSM state at the start of every message, not only the last one, there would always be a checkpoint at the end of the shared prefix, and the position of the effort block would stop mattering.

every boundarysystemtoolsuser: questioneffortassistant

Cost: a change in mlx-serve, after the current rule is confirmed in its source. More checkpoints per prompt, each with a copy of the GDN state.

5. Take the effort out of the prompt

The client pins the effort per session (the current decision), or limits thinking with a per-request budget if the server exposes one. Without the line in the prompt, the cache does not depend on the effort.

requestsystemtoolsuser: questionassistant+ thinking budget in the API call

Cost: a per-request thinking budget is not the same control as the effort line, and it was not checked whether mlx-serve exposes one.

Suggested order: options 1 and 2 together, with the Task 11 battery, because both use the overlays and scripts that exist. Option 3 as a fallback. Options 4 and 5 depend on mlx-serve.

Limits

  • GPQA-Diamond and LiveCodeBench are 50-question samples, not the full sets. Swift 1.5 has 2 rounds per effort and template, iQ-MLX has 1. A difference of 2–3 questions is within noise; the campaign rule accepts a drop of up to 3 per round.
  • The iQ-MLX xhigh official run is from another server session (2026-10-10). Its thinking ratio against the tail run (×1.05) is close to the same-session A/A at medium (×1.01), so the sessions look comparable, but it is not a same-day pair.
  • The checkpoint position (start of the last message) is inferred from the hybrid miss and inherited N checkpoints lines of the server log, not from the mlx-serve source.
  • The short-prompt probe (3f) ran only on Swift 1.5. The prompt is the same for iQ-MLX, so the cache behaviour should match, but it was not measured.
  • None of the five options in Ways to keep both was tested. They are listed as hypotheses with their expected cost.
  • LiveCodeBench answers graded by the old runner were regraded with the official import prelude; no passing answer turned into a failure.
